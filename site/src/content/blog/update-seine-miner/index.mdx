Keep seine on the latest release with the pool connection and launch settings that already work on your machine. This guide follows the public v0.3.1 release: how automatic updates work, what to do once when you come from an older version, and how to update by hand. For a first installation, use the [Windows](/blog/mine-blocknet-on-windows/), [Linux](/blog/mine-blocknet-on-linux/) or [Mac](/blog/mine-blocknet-on-mac/) setup guide.

## How do you update the seine miner?

<Answer>
Leave seine running. It checks for a new release at startup and every 12 hours, counts down 60 seconds in the dashboard header while it keeps mining, then installs the signed release and restarts with the same arguments and settings. To update by hand instead, stop seine, replace its files from the official archive and start it the same way.
</Answer>

## How do automatic updates work?

When a newer release is out, the header shows `update vX.Y.Z available`, the log links to the release, and the header then counts down: `updating to vX.Y.Z in 42s`. Mining continues during the countdown. Press `u` to update right away, or `s` to skip that version; seine remembers the skip in its data directory and offers the next release as usual.

After the countdown, seine checks the release's signature, makes sure the new executable starts, and only then replaces the old one. It stops mining cleanly and restarts with the same arguments, and the new dashboard logs `updated to seine vX.Y.Z`. The new version starts on your saved tuning and only tests what the release changed, so it is back to full speed quickly.

If a pool sends work that needs a newer release, for example at a network upgrade, seine pauses mining and installs the update right away, even a version you skipped. Pass `--no-auto-update` to keep only the notice, or `--disable-update-check` to turn the check off. Builds you compile yourself show the notice and leave the update to you.

## What do you do once when coming from an older version?

Most rigs need nothing. A few setups need one step on the first automatic update to v0.3.1:

- **Linux, from v0.2.45:** v0.2.45 installs the new version and then exits. Start seine once more. Setups that restart seine by themselves, such as a systemd service, need nothing.
- **Windows, from v0.2.45 or v0.3.0:** the old version starts the new one and exits. If a script or service also restarts seine when it exits, stop it once after the update so only one seine keeps running.
- **HiveOS and mmpOS, from the v0.3.0 package:** switch your flight sheet or profile to the v0.3.1 package from the [release page](https://github.com/zpalmtree/seine/releases). From v0.3.1 on, the package upgrades through the mining OS: change the version in its URL, as the [HiveOS and mmpOS guide](/blog/mine-blocknet-hiveos-mmpos/) shows.

## How do you check your current version?

The dashboard header shows the version you are running. You can also run the version command against the executable you actually use. An old copy in another folder can give a different answer from the miner launched by a shortcut or service. Record the executable path, working directory and startup arguments together; those three details make the update repeatable. On Windows, open PowerShell in the current miner folder:

```powershell
.\seine.exe --version
```

On Linux or macOS, use the terminal in that folder:

```sh
./seine --version
```

Compare the result with the [official releases](https://github.com/zpalmtree/seine/releases) and read the release notes for changes that affect your platform, runtime or launch options.

## Which settings should you preserve?

By default, seine reads `./seine-data/seine.config.json`. The `./` means the current working directory, so moving the executable and launching it from a new folder can also change where it looks for settings. If your command uses `--data-dir`, keep pointing it at the same directory. An absolute path makes the location explicit when shortcuts, scripts or service managers choose the working directory.

The saved configuration holds connection details such as mining mode, payout address, pool URL and rig name. Keep the whole data directory, including existing tuning files. Also save the startup command, script or service definition: options such as `--backend` and `--threads` are separate from those saved connection fields. Retaining both preserves your intended setup across the restart.

## How do you update seine by hand?

If you run with `--no-auto-update` or prefer to choose the moment yourself, update by hand. Use the [download page](/#download) or the official release page and select the archive for your operating system and CPU architecture. Download the separate `SHA256SUMS.txt` asset from the same release. Compare the archive with its matching checksum before extracting it into a separate folder. The [download-verification guide](/blog/antivirus-flags-crypto-miner/) explains the Windows checksum procedure and how to handle a download warning.

Keep all files shipped in the archive together. In particular, the Windows package includes NVIDIA runtime libraries beside `seine.exe`; copying only the executable can leave a mismatched installation. The [NVIDIA guide](/blog/mine-blocknet-nvidia-gpu/) covers runtime setup. The [v0.3.1 configuration reference](https://github.com/zpalmtree/seine/blob/v0.3.1/docs/guides/configuration.md) documents the saved configuration, automatic updates and startup behavior used here.

## Stop, back up and replace

Quit the interactive miner with `q` or `Ctrl+C` and wait for it to exit. For a managed service, use its service manager and account for any automatic restart policy before replacing files. Make a local backup of the existing application folder and data directory while the miner is stopped. Keep the backup separate from the new extraction so the two versions remain easy to identify.

Place the new application files in the installation location, preserving the original data directory. If you use versioned installation folders, update the shortcut or service executable path and explicitly retain its working directory and data path. Restart one instance with the same startup options. On multiple rigs, complete the checks below on one machine before repeating the procedure elsewhere.

## How do you confirm the update worked?

Run the version command again against the installed executable and compare it with the release you downloaded. Launch the miner and check the displayed payout destination, pool and rig name. Confirm that the intended CPU or GPU backends start. Saved tuning information can be reused when compatible; let any startup tuning complete before judging the displayed hashrate. The [dashboard guide](/blog/seine-dashboard-explained/) explains the relevant panels.

Look for accepted shares, then open [My Stats](https://bntpool.com/stats) for the same payout address. Pool estimates need arriving shares and time to settle, so an immediate hashrate difference alone does not identify an update problem. A new process also starts a new local session. Compare the address, rig and share activity before comparing short-term counters from the old and new runs.

## What if setup prompts appear again?

Check the current working directory and `--data-dir` first. A new extraction folder often has no existing configuration at its relative default path. Stop that instance and point it at your original data directory. If an error names a configuration file, preserve the file and exact message while investigating. Keep wallet seeds, private keys and control API tokens out of screenshots or public reports.

For a launch failure, record the version, operating system, executable path and exact error, then follow the matching platform guide. Your backup preserves the previous application and settings together. Before restoring an older release, check the newer release notes for compatibility requirements. Resume with a known configuration and verify accepted shares again; there is no need to recreate a wallet just to replace the miner application.
