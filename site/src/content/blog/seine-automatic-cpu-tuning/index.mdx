Understand what seine is doing when its CPU thread count changes during mining. This guide follows the public v0.3.1 release and explains how seine finds the fastest settings for your CPU, why it keeps the lowest thread count that gets there, and when it looks again. For installation, start with the [mining guide](/blog/how-to-mine-blocknet/); for the meaning of each panel, use the [dashboard tour](/blog/seine-dashboard-explained/).

## How does automatic CPU tuning work?

<Answer>
Seine starts mining right away and tunes on real mining work. It compares the CPU kernels your processor can run, then thread counts, measuring the current setting, the candidate, and the current setting again. It keeps the lowest thread count that hashes as fast as the best one, then stops testing until something changes.
</Answer>

<img src="/assets/blog/cpu-autotuning.svg" alt="A repeated baseline–candidate–baseline comparison leads to a saved setting, with memory availability checked throughout." width="1200" height="675" loading="lazy" />

Leave `--threads` unset to use automatic tuning. There is nothing to configure. Seine starts from the best it knows: this machine's saved result, then a starting point for your CPU model, then an estimate from your cores and free RAM. From there it searches in growing steps until more threads stop helping, then narrows down.

Running the current setting on both sides of each candidate means a change in load, such as a browser tab or a background update, doesn't count for or against the candidate. A candidate that is clearly slower is cut short, so most machines finish within minutes.

## What does the Tuning row on the dashboard mean?

The dashboard's `Tuning:` row says where tuning stands:

| Row | Meaning |
|---|---|
| `trying kernels, about 4 min left` | Comparing CPU kernels while mining |
| `12 vs 16 threads, about 3 min left` | Comparing two thread counts; the count moves between them while seine measures |
| `update: 12 vs 14 threads, ~2 min` | A new version changed something for your CPU and is testing just that |
| `done` | Tuned. The thread count stays put unless something changes |
| `low on RAM, best is 12 threads` | Running fewer threads until RAM is free again |

The log has one line when tuning starts, saying why, and one when it finishes, for example `tuned to 12 threads`. The [dashboard guide](/blog/seine-dashboard-explained/) covers the other panels.

## Why does seine use fewer threads than it could?

Each CPU thread holds a large memory arena, and all threads share the machine's memory bandwidth. Past a certain count, more threads add no hashrate, and they take RAM that your other programs could use. Seine therefore treats any count that matches the fastest one as just as good, and keeps the lowest of them. You get the same hashrate with more memory left free.

That is why the best count is often below your core or thread total, and why it differs between machines that look alike. Thread count, memory channels and page backing all play a part, so a result from another computer is a reference, not a setting to copy. The [RAM guide](/blog/how-much-ram-to-mine-blocknet/) explains the memory budget per thread.

If you prefer to save power and memory over the last few hashes, `--cpu-profile efficiency` keeps a lower count that is close to the fastest one.

## Does seine also tune the CPU kernel?

Yes. A kernel here is the software implementation of the hash for a given set of processor instructions. Seine checks which instructions your CPU supports, never tries a kernel it can't run, and skips kernels that don't win on your CPU. It compares the rest while mining, before it settles the thread count. Kernel switches happen between complete hashes, so mining continues and the pool connection stays up.

## When does seine tune again?

Once the row reads `done`, seine runs no scheduled tests. It looks again only when something changes:

- **A new version changes something for your CPU.** The new release starts on your saved result and tests only what changed, such as a new or improved kernel. A version that changes nothing about hashing runs no tests at all.
- **Hashrate moves for a sustained period,** for example when another program starts or stops using the CPU heavily.
- **More RAM becomes free** after RAM was what held the thread count back.
- **The hardware, operating system or CPU limits change,** such as a container's CPU limit.

Each of these writes a log line that says why tuning started. Automatic updates keep your tuning, so updating seine doesn't send it back to the start. The [update guide](/blog/update-seine-miner/) explains how updates work.

## What happens when other programs need RAM?

Seine checks free RAM once per second. When other programs need memory, CPU threads finish their current hash, park and release their arenas, and the row shows `low on RAM`. When the memory is free again, the threads come back. The best count it learned stays saved, so a short squeeze doesn't erase it.

On Linux, released explicit HugeTLB arenas return to the reserved huge-page pool; seine doesn't resize that pool. The [huge-pages guide](/blog/huge-pages-blocknet-mining/) covers reserving huge pages.

## How are saved tuning results reused?

Results are saved in `seine.cpu-autotune.json` in the data directory, `seine-data` by default. On the next start seine goes straight back to the saved result and the row reads `done`. If the hashrate is clearly different from last time, it tunes again and the log says why. Keep the same data directory between runs so seine can find the file, and let each rig build its own: copying another machine's file doesn't help, because the result depends on the exact hardware and settings.

## Can you change the thread count yourself?

Yes. Press `-` or `+` in the dashboard to remove or add one CPU thread. Once tuning reads `done`, the change applies to the running threads at once, and GPUs and the pool connection keep running. While tuning is still choosing a count, the keys wait and the dashboard shows how long tuning has left. A key press lasts for that run only; the next start uses the saved result again.

To fix a count from the start, use `--threads`, for example `--threads 4`. Seine then keeps that count and still picks the best kernel for it. `--disable-cpu-autotune-threads` turns off thread and kernel tuning altogether. The [flag reference](https://github.com/zpalmtree/seine/blob/v0.3.1/docs/MINER_FLAGS.md) documents these options, and [mining while you use your PC](/blog/mine-while-using-pc/) shows how to share a desktop with mining.

For everyday mining, start with the defaults and let tuning reach `done`. Use the CPU device row to follow a tuning trial and the [pool statistics](https://bntpool.com/blog/track-your-miner-on-bntpool/) to follow credited mining activity.
