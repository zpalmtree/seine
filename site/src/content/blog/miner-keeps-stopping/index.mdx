Get your Blocknet miner running consistently by identifying the point where it stops. This guide follows seine v0.3.1 and starts with evidence you can collect on your own computer. Keep your last working command and configuration available, then change one relevant setting at a time so the next result tells you something useful.

## What should you check when a miner stops?

<Answer>
Check whether the miner process exited, the computer slept, or the pool connection is recovering. Preserve the final message and time before restarting. Match that evidence to startup configuration, memory allocation, GPU initialization or an operating-system event, then verify the corrected launch with fresh accepted shares.
</Answer>

## Keep the final message visible

Open a terminal in your normal launch directory and run your existing command there. Add `--ui plain` if you want plain log output instead of the dashboard, keeping the other arguments unchanged. This starts mining with your existing setup. Copy the final messages, including the first error before any repeated reconnect or shutdown messages.

Record the executable version, working directory and selected data directory together. A handled fatal error is printed with `fatal:` before exit. On Windows, when you start `seine.exe` by double-clicking it, the console stays open after a fatal error until you press Enter, so you can read the message. An operating-system termination may leave different evidence. If the process remains alive, follow the [pool connection checks](https://bntpool.com/blog/track-your-miner-on-bntpool/) rather than treating a missing share or a temporary connection loss as proof of a crash.

## Did seine stop for an update?

A short stop can be an update. With automatic updates on, seine counts down in the dashboard header, installs the new release, stops mining cleanly and restarts with the same arguments; the new dashboard logs `updated to seine vX.Y.Z`. If a pool sends work that needs a newer release, for example at a network upgrade, seine pauses mining and logs `installing seine vX.Y.Z now: mining is paused until Seine is updated`, then carries on once the update is in place.

Coming from v0.2.45 on Linux, the old version installs the update and then exits, so start seine once more; a systemd service or other restarting launcher needs nothing. The [update guide](/blog/update-seine-miner/) lists the one-time steps for Windows, HiveOS and mmpOS as well.

## Does it stop before mining begins?

Read the named file, option or library in the startup message. A configuration parsing error should lead you to the specific saved file; preserve a copy before correcting its syntax. Check that a shortcut or service uses the intended working directory. The [configuration guide](/blog/configure-seine-miner/) explains why the same executable can read different settings when launched from different folders.

If the executable cannot start, confirm the correct archive for your operating system and architecture and use the official release. Follow the [download verification guide](/blog/antivirus-flags-crypto-miner/) for a security-product alert. Keep protection enabled while identifying the file and message. If the problem began after an update, compare the executable path and launch arguments with the [update procedure](/blog/update-seine-miner/).

## What if the message mentions memory or pages?

Match the requested CPU thread count to available memory, including other applications and any container limits. An allocation error identifies a resource problem to investigate; it does not by itself prove defective RAM. Close unnecessary workloads or reduce a deliberate thread override, then retry once. Keep notes about which change affected the result and whether mining actually began.

An explicitly required page mode needs the corresponding operating-system reservation. A required huge-page allocation failure and an ordinary-memory shortage are different checks. Use the [RAM guide](/blog/how-much-ram-to-mine-blocknet/) for capacity planning and the [huge-pages guide](/blog/huge-pages-blocknet-mining/) for page setup. Avoid changing several tuning flags together: a simpler known configuration makes the next log easier to interpret.

## Check the GPU stage separately

If startup names a CUDA or HIP library, device or GPU allocation, record that exact message and the installed driver version. The [NVIDIA setup guide](/blog/mine-blocknet-nvidia-gpu/) and the [AMD setup guide](/blog/mine-blocknet-amd-gpu/) cover release requirements, runtime libraries and device selection. Compare those requirements with your installed environment before changing kernel or tuning options. A successful archive download alone does not establish that the runtime is ready.

seine can isolate a backend fault while other active backends continue. If the AMD runtime closes seine twice in a row while it uses the GPU, seine stops selecting AMD cards by itself and keeps mining on the rest; start it once with `--backend cpu,amd` after a driver update to try the cards again. Check the backend messages and remaining activity before concluding the whole application stopped. Save evidence before restarting; a new session can hide the previous sequence. If you deliberately test a simpler backend selection, preserve your original command and compare startup, ongoing work and accepted submissions under the changed selection.

## Was the computer asleep or restarted?

Compare the stop time with sleep, hibernation, reboot and scheduled-task history. A screen turning off and the computer entering sleep are separate settings. On Windows, inspect the [power and sleep settings](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11) and check whether the event followed a lid close or a power-source change. Choose settings appropriate to the machine's intended use and cooling arrangements.

For an unexpected process exit, inspect the operating-system application and system logs near the same time. Windows [Event Viewer](https://learn.microsoft.com/en-us/windows/win32/cossdk/finding-the-source-of-an-error) can associate an application error with its executable. A whole-machine restart needs system-level evidence as well. On a service-managed installation, inspect the service's exit status and log before enabling repeated restarts that could obscure the original cause.

## Verify the fix and keep a useful report

Relaunch through your normal shortcut, terminal or service after the targeted correction. Confirm the destination, active backends and new accepted shares. Observe the condition that previously caused the stop, such as ordinary desktop use or the next scheduled launch, without recreating an unsafe hardware condition. Use the [dashboard guide](/blog/seine-dashboard-explained/) to distinguish current work from accumulated session statistics.

If the stop repeats, collect a concise report: version, operating system, hardware, available memory, exact launch options, time and final messages. Include what changed and whether the whole process exited or one backend stopped. Remove credentials and personal data from logs; never share a wallet seed or private keys. Preserve the working configuration and avoid guessing a cause from hashrate alone.
